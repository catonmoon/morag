# Развёртывание Mac-стека транскрибации

Ставит на **любую машину Apple Silicon** четыре сервиса, из которых состоит транскрибация:

| сервис | порт | что делает | venv |
|---|---|---|---|
| diarizer | 8090 | pyannote: кто когда говорит | `venvs/diarizer` |
| transcribe | 8123 | mlx-whisper, честно уважает `initial_prompt` | `venvs/whisper` |
| campp | 8126 | CAM++: центроиды голосов для реестра `Speaker_N` | `venvs/campp` |
| asr-adaptor | 8082 | оркестратор всего пайплайна | `venvs/adaptor` |

Код берётся **из чекаута morag** и не копируется: обновление стека = `git pull` + перезапуск.
Четыре venv, а не один, потому что версии несовместимы — pyannote прибит к `torch 2.3.1`,
адаптеру нужен свежий `torchaudio` для MMS_FA, mlx-whisper тянет свой `mlx`.

## Что нужно до начала

- **Mac на Apple Silicon.** Диаризация и выравнивание идут на MPS, whisper — на MLX; Intel не годится.
- **macOS с homebrew, `python3.12` или новее и `ffmpeg`**: `brew install python@3.12 ffmpeg`.
  Системный питон 3.9 не подойдёт — он не понимает `X | None` из кода адаптера.
- **Чекаут morag** (этот репозиторий) — код стека берётся из него, а не копируется.
- **Ключ LLM** (OpenAI-совместимый провайдер) — без него адаптер не стартует вовсе.
- **HF-токен** — только ради gated-части pyannote. Заводится на huggingface.co/settings/tokens
  (роли `read` достаточно), условия принимаются на страницах `pyannote/segmentation-3.0` и
  `pyannote/speaker-diarization-3.1`. Всё остальное качается свободно.
- **Место на диске: ~4.6 ГБ** (3.1 ГБ venv-ы + 1.5 ГБ модели) плюс 1.3 ГБ на веса MMS_FA при
  первом выравнивании. Установка занимает около десяти минут, из них большая часть — торч.

## Быстрый старт

```bash
cd services/asr-adaptor/deploy/mac
./install.sh                              # создаст ~/.asr-stack.env и остановится
#   впишите в него OR_KEY (ключ LLM) и HF_TOKEN (для gated-части pyannote)
./install.sh                              # venv-ы и зависимости (~10 мин)
./fetch-models.sh                         # модели из сети (~1.6 ГБ): whisper, CAM++, pyannote
./stack.sh up                             # поднять; диаризатор грузит модель ~90 с
./stack.sh health                         # downstream должен быть ok у всех трёх
```

`fetch-models.sh` стоит после первого `install.sh` не случайно: pyannote кладётся в кэш через
`huggingface_hub`, а тот появляется вместе с venv. Можно и раньше — тогда скрипт возьмёт любой
python, где этот пакет уже установлен.

`install.sh` идемпотентен: гоняйте сколько угодно, готовое не пересоздаётся. `./install.sh --check`
ничего не меняет и просто говорит, чего не хватает.

**Если что-то не поднялось:** `./stack.sh status` покажет, кто слушает порты и сколько ест,
`./stack.sh logs` — хвосты всех четырёх логов (они же в `~/asr-stack/logs/`). Частые причины:
пустой `OR_KEY` (адаптер не стартует вовсе — `LLMClient` строится на импорте модуля), занятый порт
и отсутствующие веса.

Проверить сквозной пайплайн, не гоняя целый выпуск: `transcribe_one.sh` принимает локальный файл
третьим способом вызова, так что короткий кусок звука проходит все стадии за минуты.

```bash
ffmpeg -ss 1800 -t 180 -i выпуск.mp3 -c copy /tmp/smoke.mp3
ASR_BASE=http://127.0.0.1:8082 ../../client/transcribe_one.sh 99 /tmp/smoke.mp3
```

Дальше — обычный прогон выпуска доменной обёрткой, только `ASR_BASE` смотрит сюда:

```bash
cd <репозиторий-проекта>/<корпус>
ASR_BASE=http://127.0.0.1:8082 SEASON=2 ./transcribe.sh 34
./stack.sh down                           # погасить, память вернуть
```

## Откуда берутся модели

| что | зачем | откуда | доступ |
|---|---|---|---|
| **whisper-podlodka-turbo** (1.5 ГиБ) | распознавание речи, оба прохода | [`chukanov/whisper-podlodka-turbo-mlx`](https://huggingface.co/chukanov/whisper-podlodka-turbo-mlx) — MLX-конверсия [`bond005/whisper-podlodka-turbo`](https://huggingface.co/bond005/whisper-podlodka-turbo) | свободно |
| **pyannote segmentation-3.0** (6 МиБ) | границы речи | `pyannote/segmentation-3.0` | **gated**: HF-токен + принятые условия |
| **pyannote speaker-diarization-3.1** (конфиг) | сборка пайплайна диаризации | `pyannote/speaker-diarization-3.1` | **gated**, там же |
| **wespeaker-voxceleb-resnet34-LM** (26 МиБ) | эмбеддер голосов для диаризации | `pyannote/wespeaker-voxceleb-resnet34-LM` | свободно |
| **CAM++ onnx** (27 МиБ) | центроиды голосов для реестра `Speaker_N` | [релизы sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx/releases/tag/speaker-recongition-models) — ONNX-сборка 3D-Speaker | свободно |
| **MMS_FA** (~1.3 ГБ) | пословное выравнивание | бандл `torchaudio` | качается сам при первом выравнивании |

Всё, кроме MMS_FA, приносит `./fetch-models.sh` — он идемпотентен и уже скачанное не трогает.
MMS_FA приезжает сам, поэтому первое выравнивание дольше на четверть часа.

⚠️ **Кэш pyannote — не тот, что у huggingface_hub.** Библиотека читает `~/.cache/torch/pyannote`
(её собственный дефолт, переопределяется `PYANNOTE_CACHE`), а не `~/.cache/huggingface/hub`.
В последнем может лежать неполная копия — и по ней легко решить, что моделей нет.

⚠️ **Диаризатор сам gated-модели не дотянет:** он зовёт `Pipeline.from_pretrained` без токена, и
`stack.sh` ему `HF_TOKEN` не передаёт. Значит pyannote надо скачать заранее — `fetch-models.sh`
это и делает.

### Что действительно нельзя скачать

**`speaker_registry.json`** — единственное, чего нет в сети: это не модель, а состояние корпуса.
Новый корпус начинает с пустого реестра — так и надо, голоса накопятся за первые прогоны. Файл
появляется сам при первом прогоне в `$ASR_STACK_HOME/state/` (или там, куда указывает
`ASR_REGISTRY_PATH`).

### ⚠️ Реестр голосов — одна копия на всех

В реестре сквозной `next_id`: локально его бережёт `flock`, между машинами блокировок нет. Если
один корпус расшифровывают на двух машинах, два прогона дадут **двух разных людей под одним
`Speaker_N`**, и наминг всего корпуса разъедется. Правило простое: у корпуса один рабочий
экземпляр реестра и один прогон за раз, записи — последовательно.

Переносится он обычным копированием файла:

```bash
rsync -a user@другая-машина:asr-stack/state/speaker_registry.json ~/asr-stack/state/
```

## Профили: несколько корпусов на одной машине

Конвейер жанра не знает и знать не должен — он одинаково обрабатывает подкаст, планёрку и запись
лекции. Отличается **корпус**: как называть материал в подсказке модели, какие термины и имена в
нём постоянны, сколько голосов ждать и в какой реестр их складывать. Всё это — переменные, поэтому
профиль корпуса это просто ещё один env-файл:

```bash
cp env.example ~/.asr-stack-work.env      # и заполнить блок «ПРОФИЛЬ КОРПУСА»
ASR_STACK_ENV=~/.asr-stack-work.env ./stack.sh up
```

```bash
ASR_CORPUS_DESC="рабочей записи: встречи, митапа или обучающего материала по разработке"
ASR_ALWAYS_TERMS="Имя Фамилия,Имя Фамилия,название продукта"
ASR_REGISTRY_PATH="$HOME/asr-stack/state/speaker_registry-work.json"
ASR_MAX_SPEAKERS=15
```

Описание корпуса подставляется в промпты правки терминов и наминга вместо зашитого «русскоязычного
подкаста про технологии». Пишите его в **родительном падеже и единственном числе** — строка встаёт
и после «расшифровку фрагмента …», и после «Тебе дано НАЧАЛО …».

⚠️ **Свой реестр голосов на корпус обязателен.** Реестр — общее пространство `Speaker_N`, и голоса
из разных проектов в нём смешиваются. Ложный voice-матч на пороге 0.55 — не теория: он уже
случался, и человека подписало чужим именем; в подкасте ошибку исправило интро, а на рабочей
записи исправлять будет нечем.

⚠️ **Голосовые отпечатки коллег — биометрия.** Реестр рабочего корпуса не место в общем репозитории.

Внутри одного корпуса жанры мешать можно: разбирать, встреча это или лекция, конвейеру не нужно.
Наминг ведёт себя консервативно — не нашёл представлений, оставит `Speaker_N`, имён не выдумает.

## Расшифровать целую папку

```bash
ASR_BASE=http://127.0.0.1:8082 ../../client/run_folder.sh ~/Records
ASR_BASE=http://127.0.0.1:8082 ../../client/run_folder.sh ~/Records --dry   # что будет сделано
```

Берёт из папки всё аудио и видео (видео разжимается в дорожку через ffmpeg) и кладёт результат
**рядом с исходником**: `Планёрка 12 марта.mp4` → `Планёрка 12 марта.md` и `.json` (пословные
тайм-коды лежат внутри json, в `x_enriched.words`).
Идемпотентно — запись с готовым `.json` пропускается, так что папку можно гонять повторно и
доливать новые файлы. Последовательно — реестр голосов общий, параллельный прогон разъедет
нумерацию `Speaker_N`. Упавшая запись не рвёт прогон, счёт сорвавшихся печатается в конце.

## Померить свою машину

```bash
./bench.sh /путь/к/выпуску.mp3          # поднимет стек, если не поднят
```

Гонит выпуск целиком и печатает таблицу: время по семи стадиям, число вызовов LLM, стоимость
(дельта по `GET /api/v1/key`), потери речи. Рядом с mp3 кладёт `<файл>.bench.json` — им и сравнивают
машины. Реестр голосов после замера **откатывается** (замер не должен оставлять следов в общем
состоянии); `--keep` отключает откат.

Сравнивать честно можно только полные выпуски: на коротком клипе фиксированные расходы (загрузка
моделей, один вызов наминга) съедают долю, несопоставимую с боевой.

## Сколько это занимает времени и памяти

Сквозной прогон записи на 5481 с звука (91 минута) на ноутбуке с 16 ГБ памяти:

| стадия | время | доля | LLM |
|---|---|---|---|
| диаризация | 293.6 с | 23.7% | |
| пасс-1 whisper | 244.9 с | 19.7% | |
| глоссарий | 102.7 с | 8.3% | 20 вызовов |
| пасс-2 whisper (360 чанков) | 360.9 с | 29.1% | |
| финал-раунд (65 реплик) | 78.4 с | 6.3% | ~143 вызова |
| наминг | 8.5 с | 0.7% | ~2 вызова |
| выравнивание слов | 144.1 с | 11.6% | |
| **итого** | **1241 с (20.7 мин)** | | **166 вызовов, 0 ошибок** |

На большой стационарной машине тот же конвейер — вдвое быстрее. **Аудио-стадии дают 84%
времени, LLM 15%**: упирается в
машину, не в сеть. Стоимость выпуска — **$0.0288** (замер по `GET /api/v1/key` до и после).

⚠️ **Токены по обычному ключу не посчитать:** `/api/v1/activity` отвечает `403 Only management
keys`, а `LLMClient` морага `usage` из ответов не логирует. Считать деньгами и ставками модели.

⚠️ **RSS у MLX-процесса ничего не значит:** веса лежат в Metal-буферах единой памяти и в RSS не
попадают — `ps` показывает 228 МБ при модели в 1.6 ГБ. Смотреть `top` по машине целиком. У pyannote
(обычный torch) RSS честный — пик 2.4 ГБ.

⚠️ **Любой прогон меняет реестр голосов, даже если все голоса уже известны:** центроиды и `next_id`
на месте, но в `provenance` дописывается выпуск, и md5 расходится. Запись бывает ложной — CAM++
может сматчить гостя с чужим центроидом, интро исправит имя в транскрипте, а провенанс уже уйдёт
не тому. Перед тестовым прогоном стоит снять копию реестра и вернуть её после.

## Память: почему не launchd

На стационарной машине стек живёт под launchd с `KeepAlive` — там памяти вдоволь и резидентные
модели ничего не стоят. На ноутбуке с 16 ГБ так нельзя: под нагрузкой машина уходила в своп на 12 ГБ, а после
`stack.sh down` возвращалось 4.4 ГБ свободной памяти. Четыре сервиса, ждущие выпуска раз в неделю,
просто отнимают память у работы — поэтому `up` / `down` руками. Плисты всё же генерируются
(`install.sh --launchd`) — для стационарной машины, где стек должен подниматься сам.

Параллелизм в `env.example` выставлен по единице (`ASR_MAX_JOBS`, `ASR_*_SLOTS`). На машине
с большой памятью его поднимают и получают выигрыш; на 16 ГБ это OOM.

## Грабли, уже пойманные на этом пути

- **`rsync` на macOS — это `openrsync`.** Он не понимает `--info=progress2` и вместо копирования
  печатает usage, завершаясь успешно: выглядит как «скопировалось», а каталог пуст. Всплывает при
  переносе реестра между машинами — флагов минимум, результат сверять `md5`.
- **Кэш pyannote — не кэш huggingface_hub.** Библиотека читает `~/.cache/torch/pyannote`; копия
  в `~/.cache/huggingface/hub` ей не видна, и стек выглядит «без моделей» при скачанных весах.
- **Значения с пробелами в `~/.asr-stack.env` обязаны быть в кавычках** — файл читается через
  `source`, и `ASR_ALWAYS_TERMS=Иван Иванов` разрывается на команду `Иванов`.
- **Питон не ниже 3.12.** Системный 3.9 не понимает `X | None` из кода адаптера.
- **`pip install $MORAG_REPO` ставит ядро в site-packages, а не читает из чекаута.** После
  `git pull`, тронувшего `src/morag/`, прогнать `install.sh` снова — иначе venv останется со старым
  ядром (ловили `TypeError` на свежем `RetryPolicy`).
- **Дефолт прослушивания у transcribe-бэкенда — loopback**, исторически было `0.0.0.0`.
  Адаптер ходит к нему по `127.0.0.1`, а открытый ASR на ноутбуке в чужой сети не нужен. Прежнее
  поведение возвращается через `TRANSCRIBE_HOST=0.0.0.0`.

## Что где лежит

```
~/asr-stack/            ← ASR_STACK_HOME, всё состояние машины
  models/                 whisper-podlodka-turbo/, CAM++ .onnx
  state/                  speaker_registry.json
  venvs/                  whisper/ diarizer/ campp/ adaptor/
  logs/  run/             логи и pid-файлы stack.sh
~/.asr-stack.env        ← секреты, 0600, НЕ в git
~/.cache/torch/pyannote ← веса pyannote (путь задан самим pyannote)
```
