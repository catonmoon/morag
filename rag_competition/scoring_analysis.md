# Анализ метрик RAG-соревнования ARLC

## Формула скоринга

```
Total = (0.7 × S_det + 0.3 × S_asst) × G × T × F
```

**Total** — итоговый балл, определяет место в рейтинге.

## Компоненты

### S_det — точность детерминистичных ответов (вес 0.7)

Оценка ответов с фиксированным форматом:

| Тип | Метрика | Пример |
|-----|---------|--------|
| boolean | exact match | true/false |
| number | ±1% допуск | 34559.76 |
| name | exact match | "H.E. Justice Shamlan Al Sawalehi" |
| names | Jaccard similarity | ["Omid", "Orah"] |
| date | ISO exact match | 2025-10-22 |

**Что показывает**: способность RAG найти конкретный факт в корпусе и точно его извлечь.
Высокий S_det = хороший retrieval + корректная экстракция LLM.

**Наш результат**: 0.986 — почти идеальный. Ошибки в ~1.4% случаев (edge cases: casing имён, формат дат).

### S_asst — качество свободных ответов (вес 0.3)

LLM-judge оценивает free_text ответы по 5 критериям (0-1 каждый).
Оценивает полноту, точность, релевантность формулировки.

**Что показывает**: способность RAG сформулировать развёрнутый ответ на основе найденных документов.

**Наш результат**: 0.733 — средний. LLM может пропустить детали или неточно сформулировать.

### G — Grounding (МНОЖИТЕЛЬ — самый важный!)

```
G = F-beta(β=2.5) по страницам
```

Сравнивает `retrieved_chunk_pages` (какие страницы мы указали) с golden pages (правильные).

| Ситуация | G |
|----------|---|
| Оба пустых | 1.0 |
| Один пустой, другой нет | 0.0 |
| β=2.5 → recall важнее precision | |

**Что показывает**: насколько точно RAG привязывает ответ к конкретным страницам документа.
Это **множитель** — если G=0.5, даже идеальные ответы дадут Total×0.5.

**Почему β=2.5**: recall важнее — лучше указать лишние страницы (precision↓), чем пропустить правильные (recall↓).

**Наш результат**: 0.901. Page pinning дал скачок 0.757→0.901.

### T — Телеметрия

| Состояние | T |
|-----------|---|
| Корректная | 1.0 |
| Malformed | 0.9 |

**Что показывает**: корректность формата submission (JSON, все поля на месте).

**Наш результат**: 0.996.

### F — TTFT фактор (Time To First Token)

| TTFT | F |
|------|---|
| <1с | 1.05 (бонус +5%) |
| <2с | 1.02 |
| <3с | 1.0 |
| >3с | 0.85-0.99 (штраф) |

**Что показывает**: латентность ответа. Быстрый RAG получает бонус, медленный — штраф.

**Наш результат**: 3928ms → F=0.955 (штраф 4.5%). Причина: reasoning модель для select.

## Декомпозиция Total

```
Total = (0.7 × 0.986 + 0.3 × 0.733) × 0.901 × 0.996 × 0.955
      = (0.690 + 0.220) × 0.901 × 0.996 × 0.955
      = 0.910 × 0.901 × 0.996 × 0.955
      = 0.910 × 0.857
      = 0.780
```

Базовый score (S_det + S_asst) = 0.910 — высокий.
Множители (G × T × F) = 0.857 — теряем 14.3% на grounding и TTFT.

## Что улучшать (по эффекту)

### 1. Grounding G: 0.901 → 0.95 (+5.4% Total)

Главный рычаг — это множитель. Каждый +0.01 G = +1% Total.

Методы:
- Page pinning (страницы 1-3 упомянутых дел)
- Точнее `chunks_used` — сужать retrieval до реально использованных чанков
- BM25 как третий сигнал (добавлен в публичном этапе)

### 2. TTFT F: 0.955 → 1.05 (+10% Total!)

Если снизить TTFT с 3.9с до <1с — бонус +5% вместо штрафа -4.5%.

Методы:
- Убрать reasoning из select (non-reasoning модель)
- Кеширование embeddings для частых запросов
- Предварительный прогрев модели

### 3. S_asst: 0.733 → 0.85 (+3.5% Total)

Промпт для free_text ответов.

Методы:
- Более детальный промпт с примерами
- Reasoning модель для free_text (но TTFT↑)
- Chain-of-thought

### 4. S_det: 0.986 → 1.0 (+1% Total)

Edge cases: casing имён, формат сумм, даты.

## Глубокий анализ телеметрии

### Что телеметрия рассказывает о RAG-системе

Телеметрия — не просто техническая информация. Она раскрывает архитектурные решения и их последствия.

### Timing — скорость ответа

| Поле | Что измеряет | Что показывает организаторам |
|------|-------------|----------------------------|
| `ttft_ms` | Время до первого токена ответа | Включает retrieval + select + начало генерации. Показывает общую латентность пайплайна |
| `tpot_ms` | Время на токен | Скорость генерации LLM. Зависит от модели и провайдера |
| `total_time_ms` | Полное время | ttft + генерация. Разница total-ttft = время генерации ответа |

### Retrieval — привязка к источникам

| Поле | Что измеряет | Что показывает организаторам |
|------|-------------|----------------------------|
| `doc_id` | SHA хеш документа | Какой документ нашла система |
| `page_numbers` | Номера страниц PDF | На каких страницах найден ответ — основа для Grounding |

Retrieval — самая критичная часть телеметрии. Именно по ней считается Grounding (множитель).

### Usage — потребление токенов

| Поле | Что измеряет | Что показывает организаторам |
|------|-------------|----------------------------|
| `input_tokens` | Токены промпта | Сколько контекста мы даём LLM. Больше = больше чанков в промпте |
| `output_tokens` | Токены ответа | Насколько лаконична модель |

### Model — какая модель отвечает

`model_name` показывает какую LLM мы используем для финального ответа.

## Эволюция нашей телеметрии

### Хронология submission-ов

| Submission | TTFT avg | <1с | >3с | Input tok | Pages/answer | Null | Empty retr |
|-----------|---------|-----|-----|-----------|-------------|------|-----------|
| qwen (ранний, 10 отв.) | 1698ms | 40% | 20% | 10316 | 1.2 | 2 | 2 |
| grok0 | 1296ms | 55% | 1% | 1862 | 2.2 | 11 | 18 |
| grok3 | 3255ms | 39% | 40% | 2396 | 3.0 | 1 | 7 |
| grok5 | 2982ms | 43% | 37% | 2089 | 2.2 | 0 | 4 |
| v11 (место 49) | 3288ms | 8% | 41% | 2055 | 2.6 | 0 | 4 |
| latest (место 32) | 2951ms | 11% | 46% | 2091 | 2.3 | 0 | 4 |

### Что видно из эволюции

**qwen → grok0**: input tokens упали 10316 → 1862. Мы перестали отправлять весь контекст — стали отбирать чанки через select. Но 11 null ответов и 18 пустых retrieval — select был слишком агрессивен.

**grok0 → grok3**: TTFT вырос 1296 → 3255ms. Добавили reasoning модель для select — точнее, но медленнее. Null ответы 11 → 1, empty retrieval 18 → 7 — select стал лучше.

**grok3 → grok5 → v11**: стабилизация. Null = 0, empty retrieval = 4. Тюнинг промптов, page pinning.

**v11 → latest (32 место)**: TTFT чуть лучше (3288 → 2951ms). Pages/answer 2.6 → 2.3 — точнее retrieval (меньше лишних страниц).

### Что телеметрия говорит о нашей архитектуре

1. **TTFT ~3с** — у нас многоступенчатый пайплайн (intent → search → select → answer). Select с reasoning — bottleneck. Те кто делает single-shot RAG получают <1с и бонус.

2. **Input tokens ~2000** — мы отправляем отобранные чанки, не весь корпус. Типичный промпт: 5-10 чанков по 200 ток + системный промпт + вопрос.

3. **Output tokens ~26** — ответы лаконичны (boolean, число, короткое имя). Для free_text больше, но в среднем — мало.

4. **Pages/answer ~2.3** — привязываем к 2-3 страницам в среднем. Для grounding нужен баланс: слишком мало = пропустим правильную страницу (recall↓), слишком много = лишние страницы (precision↓).

5. **Empty retrieval = 4** — 4 вопроса без привязки к страницам. Если golden answer тоже без страниц = 1.0, если нет = 0.0 grounding. Риск.

6. **Null = 0** — мы никогда не отвечаем "нет информации". Агрессивная стратегия: всегда пытаемся ответить. Если golden = null, мы теряем.

### answer

- `null` = "информации нет в корпусе" (оба null → 1.0, один null → 0.0)
- `doc_id` = SHA256 filename без `.md`
- `page_numbers` = физические 1-based страницы PDF

### Стратегия null ответов

Критично: если golden answer = null и мы ответили не-null → S_det для этого вопроса = 0.
И наоборот. Лучше осторожно давать null только когда уверены.

## Наш пайплайн ответа

```
Question → Intent (Grok non-reasoning, 1-3 поисковых запроса)
  → Hybrid Search (RRF: FRIDA dense + GTE sparse + BM25)
    → Sort (группировка по документу, лучший RRF-скор первый)
      → Select (Grok reasoning, выбор релевантных чанков)
        → Retry (если select=0, уточняющие запросы)
          → Answer (Grok non-reasoning, JSON ответ)
            → Retrieval refs (страницы из chunks_used)
```

Bottleneck для TTFT: Select с reasoning (~3с).
