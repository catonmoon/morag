# ADR-0028: Сужение `search` по документам — фильтр базы, а не пост-фильтр; подсказка автозагрузки — из конфига

## Статус

**Принято** (2026-09-15). Без конфига поведение прежнее там, где сужения нет: `search` без
`section_ids`/`doc_ids` строит те же Prefetch'и, что и раньше; текст подсказки автозагрузки при
пустом `retrieval.prompts.auto_fetch_note` — байт в байт прежний.

## Контекст

ADR-0026 перевёл `filters` (поля payload) внутрь гибридного поиска, а `section_ids`/`doc_ids`
оставил **пост-фильтром по безфильтровому top-N**: чанки нужного документа обязаны были сами
попасть в общую полусотню, иначе сужение молча снималось и агент получал выдачу по всему корпусу
с пометкой «искал по всему корпусу». Для раздела это деградация; для вопроса **про один документ**
— провал: замерено на корпусе расшифровок (вопрос «перескажи эту запись» с `doc_id` записи в
тексте) — ответ собирался из **шести** записей, цитаты чужих документов шли в ответ наравне со
своими. Индекс `doc_id` у коллекции чанков при этом существует с рождения (каскадное удаление).

Вторая причина того же ухода — **автозагрузка ссылок** (детерминированная загрузка страниц по
распознанным в вопросе id): вместе с содержимым агенту впрыскивается зашитый текст «это отправная
точка, а не ответ; по умолчанию ДОИЩИ в базе контекст вокруг… для анализа поиск по базе
ОБЯЗАТЕЛЕН». Для документного корпуса это верно — ссылка задаёт отправную точку. Для корпуса, где
загруженный документ И ЕСТЬ предмет вопроса, это прямой приказ уйти из него.

## Решение

1. **`section_ids`/`doc_ids` → тот же Qdrant-фильтр, что и `filters`.** Раздел раскрывается в
   потомков (`_get_descendant_doc_ids`, как раньше), объединённое множество кладётся в
   `filters['doc_id']` и уезжает в каждый Prefetch через `build_payload_filter`. Пост-фильтр и
   откат реранкера «на нефильтрованный набор» удалены: другого набора больше нет.
   Пустая выдача с сужением — **отказ, а не второй поиск по корпусу**: фильтр по документу
   отдаёт все его чанки, ранжированные запросом, и пусто означает «таких документов нет»
   (id собран по аналогии). Агенту это говорится словами и предлагается позвать `search` без
   сужения — явно, а не за его спиной.
2. **Подсказка автозагрузки — `retrieval.prompts.auto_fetch_note`** (строка; пусто → зашитый
   дефолт). Корпус, где вопрос — про загруженный документ, пишет своё: «запись загружена целиком,
   отвечай по ней; инструменты — если загруженного не хватает».

## Почему не иначе

- **Не «усилить текст вопроса».** Ограничение в тексте проигрывает трём механизмам разом:
  пост-фильтру (снимается без участия модели), подсказке автозагрузки (последнее сообщение перед
  ходом, модель его выполняет) и секции `admin` («ОБЯЗАТЕЛЬНО дополнительный поиск по всей базе»,
  перекрывается конфигом и без этого ADR). Уговоры не лечат то, что делает код.
- **Не отдельный параметр «строгое сужение».** Сужение, которое иногда не сужает, — не сужение;
  двух режимов у одного аргумента быть не должно.
- **Не откатываться на корпус при пустой выдаче.** Прежний откат был «молчаливым с пометкой»:
  агент видел выдачу и пометку в одном блоке и продолжал отвечать по чужому. Отказ дешевле:
  один лишний ход только в случае несуществующего id.

## Границы

- `doc_id` — единственное поле сужения; `section_ids` по-прежнему раскрываются в документы
  (потомки), а не фильтруются по полю `parent_doc_ids` — семантика раздела не меняется.
- `MatchAny` по сотням `doc_id` (потомки крупного раздела): индекс KEYWORD на `doc_id` есть,
  Qdrant это держит; отдельно не мерилось.
- Статус-строка «на страницах: …» печатается по аргументам агента — теперь она означает факт
  (фильтр применён), а не намерение.

## Проверено

`tests/retrieval/test_search_scope.py`: doc_ids и потомки раздела уезжают в `_search` фильтром по
`doc_id`; фильтр агента и сужение складываются; пустая выдача с сужением — один вызов `_search` и
отказ; без сужения фильтра по документу нет; подсказка автозагрузки перекрывается конфигом, а
пустая и пробельная — дефолт. Замер на живом корпусе (вопрос к одной записи, три записи × три
вопроса, до/после) — на стороне корпуса расшифровок.
