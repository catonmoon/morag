# ADR-0006: Passthrough Fallback для больших документов и Context Window

## Статус

Принято (2026-03-22)

## Контекст

SemanticChunker использует жадный L→R алгоритм с embed_batch для определения
границ чанков. На больших документах (>32K токенов) это приводит к:

- Тысячам embed_batch вызовов к GPU
- GPU загружен на 100%, event loop заблокирован (даже с run_in_executor)
- Документ на 200K токенов (DIFC Courts Rules, 537 страниц) чанкуется 30+ минут
- В это время LLM-корутины простаивают

Параллельно, для генерации контекста чанка отправляется **весь документ** (до 130K токенов
после обрезки по context window). Для больших документов:
- Огромный prompt = медленнее, дороже
- Обрезка с начала — LLM видит только первые 130K, чанк из конца документа теряет контекст

## Решение

### 1. Passthrough fallback (`passthrough_threshold`)

Если документ > `passthrough_threshold` токенов — passthrough вместо SemanticChunker:

```
MarkdownHeaderSplitter → блоки → merge мелких (min 128, max 256 tok) → чанки
```

Без embed_batch, без GPU. Секунды вместо минут.

```yaml
indexing:
  chunker:
    passthrough_threshold: 32000  # >32K tok → passthrough
```

#### Merge логика

Блоки после MarkdownHeaderSplitter часто мелкие (номера статей, заголовки — 5-30 ток).
Алгоритм мержа:
- Накапливает блоки пока < min_tokens (128)
- Сбрасывает когда >= min_tokens или следующий блок не влезет в max_tokens (256)
- Последний мелкий кусок приклеивается к предыдущему
- Гарантия: 0 чанков < min_tokens

#### Результаты на реальных документах

| Документ | Токены | Блоки | Чанки | Время |
|----------|--------|-------|-------|-------|
| DIFC Courts Rules (8f507f...) | 199 650 | 2 474 | 740 | ~2с |
| 9b05a9... | 35 766 | 255 | 122 | ~1с |

Vs SemanticChunker: 200K документ → 2474 units → 30+ минут.

#### Затронутые документы

При threshold=32K → 7 документов из 300 (2.3%) идут через passthrough.
Остальные 293 — semantic chunking как обычно.

#### Известные ограничения

Неделимые блоки > max_tokens (длинные статьи без подзаголовков) остаются как есть.
На документе 200K: 48 чанков > 512 ток, max 2470 ток.

### 2. Context window (`window_tokens`)

Вместо отправки всего документа для генерации контекста чанка — окно текста
вокруг страницы чанка + doc_summary:

```yaml
indexing:
  context:
    window_tokens: 16384  # 16K ток вокруг страницы чанка
```

#### Новый промпт

```
Document summary: {doc_summary}       ← всегда целиком
Surrounding text: {window ~16K}       ← окно вокруг <!-- page:N -->
Chunk: {chunk_text}
```

#### Алгоритм определения окна

1. Ищет `<!-- page:N -->` маркер в тексте чанка
2. Находит позицию этой страницы в полном документе
3. Берёт ±window/2 токенов в каждую сторону
4. Fallback: если нет маркера — первые window_tokens от начала

#### Преимущества

- Для больших документов (200K ток): 16K вместо 130K в промпте
- LLM видит **релевантный** контекст вокруг чанка, а не только начало документа
- doc_summary даёт общую картину — тема документа не теряется при обрезке
- Меньше токенов = быстрее ответ, дешевле

## Реализация

| Компонент | Файл | Изменение |
|-----------|------|-----------|
| `IndexingPipeline` | `pipeline.py` | `_passthrough_chunk()` — presplit + merge, `passthrough_threshold` параметр |
| `LLMContextGenerator` | `context.py` | `window_tokens` параметр, `_extract_window()`, промпт с doc_summary |
| `ChunkerConfig` | `config.py` | `passthrough_threshold: int \| None` |
| `ContextConfig` | `config.py` | `window_tokens: int \| None` |

## Последствия

- Индексация больших документов ускорена на порядки (30 мин → 2с для chunking)
- GPU bottleneck устранён для документов > threshold
- Качество контекстов улучшено для чанков из середины/конца больших документов
  (локальное окно vs обрезанное начало)
- Для малых документов (<32K) — без изменений, semantic chunking + полный текст
