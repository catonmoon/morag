# ADR-0033: Полосы по устройствам — модель → полоса, черновик другой школы, наложение по полосам

## Статус

**Черновик, 2026-10-16; принимается по итогам стенда** (пять эталонных записей встреч, 185 минут, выверенных
владельцем целиком; критерий назван до замера — см. «Критерий»). Код — ветка `asr-speed`, всё за ручками;
без них конвейер байт в байт прежний (золотые снимки `tests/asr_adaptor/golden/` не менялись).

## Контекст

ADR-0030 дал конвейеру второе ухо другой школы, ADR-0032 — корректор, у которого на каждое помеченное место два
прослушивания. Второе ухо встреч — GigaAM-v3 (Conformer RNN-T, torch, CPU): как ухо не хуже whisper-large-v3
другой школы, при 25 с звука за секунду на CPU против десяти. Казалось, что CPU-модель бесплатна: GPU занят
whisper, CPU простаивает.

Замер на пяти записях показал другое. Разложение времени (2899 с на 185 минут, 15.7 мин на час записи):

| стадия | с | доля | ресурс |
|---|---:|---:|---|
| диаризация | 482 | 17 % | GPU |
| пасс-1 (черновик whisper, запись целиком) | 343 | 12 % | GPU |
| пасс-2 (whisper по кускам, по одному) | 631 | 22 % | GPU |
| арбитраж (читатель → второе ухо → чистое ухо) | 444 | 15 % | LLM + CPU + GPU |
| корректор (детектор → два уха на пометку → решатель) | 598 | 21 % | LLM + GPU + CPU |
| финал-раунд, глоссарий | 217 | 7 % | LLM |
| выравнивание, прочее | 184 | 6 % | GPU |

Три факта из кода, которые это объясняют:

1. **Бэкенд транскрипции — один процесс с одним потоком инференса.** mlx-whisper (GPU) и GigaAM (CPU) стояли в
   одной очереди: второе ухо на CPU ждало, пока GPU додекодирует чужой кусок, и наоборот. Поверх — один семафор
   адаптера на все уши. «CPU-модель» не выигрывала ничего.
2. **Корректор слушал два уха по очереди** внутри каждой пометки, а пометки одной реплики — тоже по очереди:
   598 с = около двух секунд на пометку, и это очередь ушей, а не LLM (детектор и решатель шли по шесть разом).
3. **Пасс-1 whisper занимает GPU ради черновика**, который нужен только глоссарию, подсказкам и разрезу на куски —
   а потом тот же звук GPU слушает ещё раз, по кускам с подсказками.

Отдельное требование владельца: конвейер должен настраиваться под машину (сейчас Mac, потом Windows и
видеокарты), не теряя событий для окна загрузки; а голоса узнавать до чистового прохода, чтобы имена спикеров
попадали в подсказки и в чистовые правки (сегодня промпты видят метку кластера диаризации, которая никому не
говорит ничего).

## Решения

### 1. Полоса — единица расписания; модель едет по своей полосе

**Полоса** = имя + класс устройства (`gpu | cpu | remote`) + слоты + адреса бэкендов. Имя полосы — имя семафора
адаптера (`pipeline._res`); адреса — её процессы (кусок уходит наименее занятому). Описание — машинная ручка
`ASR_LANES="имя=устройство,слоты,url[,url…];…"`, привязка — `ASR_MODEL_LANES="модель=полоса,…"`. Полоса по
умолчанию `whisper` описана прежними ручками и в `ASR_LANES` не перечисляется: без переменных — прежнее
поведение. `stack.sh` поднимает процесс того же бэкенда на каждый локальный адрес полосы; удалённый адрес —
просто адрес (модель на другой машине или видеокарте подключается без правки кода).

Почему процесс, а не второй поток в том же бэкенде: у обоих декодеров питоновский цикл по токенам, два потока
инференса делили бы GIL; у бэкенда есть история падения внутри MLX (стек), и изоляция процессом её не
усугубляет; и процесс — это то же самое, что удалённый адрес, то есть одна механика покрывает и ноутбук, и
сервер с несколькими машинами.

Почему адаптер не спрашивает бэкенд, какого движка модель: карта «модель → полоса» — решение владельца машины,
а не свойство модели (та же GigaAM на видеокарте — полоса `gpu`); сетевой вопрос при старте превратил бы
конфигурацию в гадание.

### 2. Уши — рядом, не по очереди

Уши корректора на одной пометке зовутся `asyncio.gather`, каждое под ресурсом своей полосы; порядок ответа —
прежний (из него строятся строки `УШИ[…]` промпта решателя и `why` правки). Уши арбитража и так шли по кускам
разом — им хватило раздельных семафоров.

### 3. Черновик другой школы вместо пасса-1 whisper, второе ухо — из черновика

`ASR_DRAFT_MODEL` — модель пасса-1 (пусто — модель профиля, как было). Для модели без длинного режима бэкенд
режет запись сам: граница части — самая тихая точка окна [20, 24] с (RMS по кадрам 20 мс), слова с временами
(RNN-T, покадрово), сегменты по знакам конца предложения и паузам ≥ 0.6 с; ответ той же формы, что у
mlx-whisper с `word_timestamps`. Разрез на куски берёт слова и режет по паузам между ними. Длинный путь
включается только по просьбе `word_timestamps` — короткое ухо на кусках арбитража идёт прежним путём, байт в байт.

`ASR_SECOND_FROM_DRAFT=1`: второе ухо арбитража и корректора берёт слова черновика из своего окна, не
переслушивая. Основание: второе ухо и черновик — одна модель без подсказки; различается только окно, а
окно без разгона модели другой школы не портит так, как whisper (ADR-0030 мерил это для whisper). Нет слов в
окне — прежний запрос к бэкенду. Стоимость такого уха в счётчике — ноль секунд звука: `audio_s` считает
только прослушанное.

Чего это НЕ меняет: основной текст — whisper с подсказками (пасс-2), арбитраж — те же правила под тем же
вето, корректор — те же уши и решатель. Меняется источник черновика и способ получить мнение второго уха.

### 4. Расписание — из полос, не из новой ручки

`ASR_OVERLAP=1` (наложение GPU на LLM внутри записи) с черновиком на не-GPU полосе кладёт пасс-1 рядом с
диаризацией: `gather(диаризация, черновик → сводка фоном → глоссарий)`. GPU на GPU по-прежнему не кладётся
(замер 13.10: обе стадии вдвое медленнее). Та же конфигурация на машине без CPU-полосы возвращается к старому
порядку сама — расписание выводится из того, где живёт модель.

### 5. Ранние голоса: имена спикеров до чистового прохода

Три уровня, которые нельзя смешивать: метка кластера диаризации (`SPEAKER_X`, центроид этой записи) →
голос реестра (`Speaker_N`, один на корпус) → имя человека. Пайплайну полезен именованный спикер; метка
кластера в промпте бесполезна. `ASR_VOICES_EARLY=1`: узел `voices` сразу после диаризации считает центроиды
кластеров по отрезкам, узнаёт их реестром (под билетом порядка), берёт имена из реестра и из карты
`hints.speaker_names` (её даёт вызывающий: словарь имён корпуса); имена узнанных — в подсказку пасса-2 (канон
написания фамилий), в контекст финал-раунда и корректора — имя вместо метки. Данные несут все три уровня;
имя живёт только в слое промптов и показа. Кластеры, появившиеся после пасса-2 (`recover`), узнаются поздним
узлом как прежде, под файловым замком без билета: держать билет от ранней записи до поздней значило бы
выстроить задачи очереди в цепочку.

Имя идёт в подсказки и промпты только уверенному матчу: `ASR_VOICES_NAME_COS` (0.75) строже порога самого матча
(`ASR_MATCH_THRESHOLD`; у корпуса встреч 0.75, как у его серверного реестра; умолчание движка 0.55 рассчитано на
подкаст с несколькими голосами). Ложный матч подсунул бы чужую фамилию в подсказку пасса-2, и модель её
«услышит»; голос без имени остаётся номером и реестру по-прежнему полезен (решение — в журнале голосов).

### 6. Очередь сервера: общий замок GPU

`ASR_GPU_GATE=1`: родительский семафор на все ресурсы устройства `gpu` (полосы gpu, диаризация,
выравнивание) поверх их собственных — две задачи (`ASR_MAX_JOBS=2`) не пересекаются на GPU, а CPU-полоса и LLM
свободны. Дочерний семафор берётся первым, родительский вторым; `wait_gpu_s` — ожидание родительского.

### 7. Переносимость — контракт бэкенда, а не код адаптера

Адаптер говорит с бэкендами по HTTP (OpenAI-совместимая форма `/v1/audio/transcriptions`: `model, language,
prompt, temperature, word_timestamps, response_format=verbose_json` → `segments[].words {word, start, end}`;
`/v1/models` с движком в `owned_by`; `/health`, `/warmup`, `/stats`) и устройств не знает. Бэкенд под CUDA или
Windows — соседняя реализация того же контракта; чистая логика разреза и сборки сегментов вынесена в модуль без
torch и mlx (`backends/transcribe/cutting.py`) и переиспользуется. Устройства бэкендов — их ручки
(`DIARIZER_DEVICE`, `ASR_ALIGN_DEVICE`, `GIGAAM_DEVICE`); потоки CPU-модели — `GIGAAM_THREADS`.

## Критерий (назван до замера)

Качество — как у профиля с корректором в пределах шума: WER не хуже более чем на 0.1 пункта (шум базы между
прогонами 0.02, разброс конфигурации до 0.12), мест правок не меньше чем на 12 (шум 11), «выдумано на тишине»
не больше. Конфигурации, меняющие только порядок вычислений (полосы, наложение, пул, очередь), обязаны дать
WER в шуме — иначе это ошибка, а не компромисс. Черновик другой школы и имена в промптах меняют текст — по два
прогона. Берётся самая быстрая конфигурация с качеством в шуме; цель ≤ 10–11 минут на час записи.

## Замеры

### Пробы до кода

- Потоки torch у GigaAM-v3 (RNN-T) мешают: на 5 минутах звука 1–2 потока — 1.32 с на минуту (×45 реального
  времени), 4 — 1.47, 8 — 1.95, 12 — 2.51. Декодер упирается в питоновский цикл по токенам. Умолчание — 2.
- Черновик записи целиком — 1.30 с на минуту звука (185 минут за 239 с): час записи — 78 с, прячется под
  диаризацией (90–130 с на час) целиком.
- WER черновика GigaAM против эталона — 6.8–16.3 % по записям против 3.35 % у конвейера: как основа текста
  модель не годится, как черновик для глоссария и разреза — проверяется прогоном. Латиницу пишет вдвое реже
  эталона (половина латинских терминов придёт кириллицей).
- Разрезов по тихой точке, попавших в речь, — 10 из 507 частей (все на самой плотной записи); слова с
  временами: длительность медиана 0.20 с, паузы ≥ 0.6 с — одна на 11 слов.
- Проба 5 минут через адаптер с CPU-полосой: 86 с против 145 с без полосы; полоса отслушала 17 запросов своим
  процессом (7.2 с инференса на 200 с звука), whisper — 39.

## Последствия

- Машинный env получает три ручки полос и четыре ручки расписания; профиль качества их не содержит. Пресеты
  машин — в `deploy/mac/env.example` с числами замера.
- Новые ключи `timing` — только с суффиксом `_s` (`arbitrate_second_s`, `arbitrate_clean_s`,
  `proofread_detect_s`, `proofread_ears_s`, `proofread_llm_s`, `wait_<полоса>_s`, `busy_<полоса>_s`,
  `wait_gpu_s`): золотые снимки режут из `timing` только такие ключи.
- Счётчики бэкенда (`/stats`) различают движки (`requests_cpu`, `infer_cpu_s`, `audio_cpu_s`): перегрузка
  весов и работа каждой полосы видны числом.
- События конвейера сохраняют имена и форму; стадии, идущие рядом (новая форма наложения), несут `parallel: true`
  в `stage.start`/`stage.end` — потребитель (окно загрузки) может показать несколько активных стадий, а не
  чехарду «текущей»; прежняя форма наложения и её снимок событий не менялись.
- Отвергнуто: второй поток инференса в одном процессе (GIL, общий стек MLX); узнавание голосов параллельно
  финал-раунду (узел пишет метку, которую читают промпты, — она менялась бы посреди стадии); диаризация на
  CPU (длинный шест).
