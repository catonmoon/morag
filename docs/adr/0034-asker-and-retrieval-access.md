# ADR-0034: «Кто спрашивает» и доступ на ретриве

## Статус

**Принято** (2026-10-19). Без секции `retrieval.access` в конфиге поведение прежнее байт в байт:
фильтры, Prefetch'и, Карта и перечни значений — те же, что до этого ADR (закреплено тестом-снимком).

## Контекст

Агент видит весь индекс. Поэтому закрытое туда не кладут: корпус с личными документами держит их
вне `sources[].path`, источник с ограничениями чтения не индексируется вовсе. Это работает, но
закрывает половину пользы: владелец личного документа не находит его поиском, а закрытые страницы
не годятся для RAG ни для кого, включая тех, кому они открыты.

Нужно обратное: индексировать всё, а на ретриве **не отдавать агенту ни одного фрагмента, который
спрашивающему не положено видеть**. Два живых случая, один механизм:

- **права знает вызывающий** — сайт поверх движка: автор документа, кому его открыли по ссылке,
  в каком подразделении человек (с иерархией: руководитель видит своё подразделение и ниже);
- **права знает источник** — вики со своими ограничениями чтения страниц и пространств, группы
  синхронизированы из каталога (LDAP).

Что мешает сегодня (замерено по коду):

- `pipe(user_message, model_id, messages, body)` не читает `body` — канала «кто спрашивает» нет;
- документ доходит до агента восемью путями: `search`, `find_section` (поиски и сводки),
  `get_doc` (и через него `lookup`), `catalog`, перечень значений фильтров в схеме `search`,
  автозагрузка ссылок из вопроса (включая живую загрузку мимо индекса), Карта знаний;
- генератор `pipe()` не сериализован (`_loop_lock` держится на один `_run()`), запросы чередуются —
  контекст запроса на `self` или в contextvar ненадёжен.

## Решение

1. **«Кто спрашивает» — подписанное поле запроса.** Вызывающий кладёт в тело
   `asker = {id, key, scope?, user?}`. Модель его не видит: поле читает только код движка.
   - `id` — непрозрачная строка с источником учётки (`ldap:kuznetsova` и `local:kuznetsova` —
     разные люди: иначе локальная учётка с тем же логином получила бы чужие права).
   - `key` сверяется с секретом из окружения (`hmac.compare_digest`). Неверный — ответ-ошибка, а
     не тихое понижение прав. Поля нет — запрос анонимный: видно только открытое всем.
   - `scope` — фильтры, которые выбрал человек на сайте (`{поле: [значения]}`, поля — те же, что
     у фильтров агента, ADR-0026). Если есть — обязательное условие поиска: агент своими
     фильтрами только сужает внутри, первой строкой выдачи видит «искал в: …», пустая выдача —
     честный отказ, а не поиск по корпусу (как в ADR-0028).
   - `user` — непрозрачный словарь сведений о человеке. В этом ADR только доезжает до
     инструментов; персонализация ответа и инструменты «про людей» — следующими ADR.
2. **Хозяин прав — внешний сервис**, движок спрашивает его по HTTP (адрес и ключ — конфиг):
   - `principals(id)` → строки, которые человек «проходит»: свои, открытые ему документы,
     подразделения с уже раскрытой иерархией, группы. Вызывающий их не присылает — их может быть
     сотни, и они меняются чаще, чем живёт разговор. Кэш на минуты.
   - `check(id, doc_ids)` → какие из документов ему можно сейчас. **Живая проверка** перед тем,
     как фрагменты уйдут агенту.
   Движок не знает ни иерархии, ни ролей — сравнивает строки. Особого случая «админ» нет.
3. **Метка на документе** — поле payload `access`: список строк «кому можно». Нет поля или
   пустой список — открыт всем. Поле доезжает до каждого чанка без правки ядра (весь payload
   документа копируется в чанк при индексации).
4. **Копия прав в индексе — для качества, правда — у хозяина.** В каждый поиск идёт отдельное
   обязательное условие `access пусто ИЛИ access ∩ principals ≠ ∅` — не через `filters` агента:
   их перезаписывает сужение по документам. В условие попадают только принципалы, встречающиеся
   в метках индекса: у человека сотни групп, в метках — десятки. Фильтр внутри поиска находит
   лучшее среди доступного, а не остаток лучшего вообще (урок ADR-0028). Отставание копии
   безопасно: закрытое ловит живая проверка, открытое найдётся после сверки.
5. **Восемь путей закрыты одним правилом.** Поиски (`search`, `find_section`) — условием в каждом
   Prefetch; точечные (`get_doc`, `lookup`, автозагрузка) — проверкой документа; `catalog` —
   условием скролла; перечень значений фильтров и Карта знаний строятся только из открытых всем
   документов (они общие на все запросы). Живая загрузка мимо индекса при включённом доступе не
   вызывается: у неё нет метки. **Закрытое неотличимо от несуществующего** — тот же текст отказа.
6. **Метки обновляются без переэмбеддинга.** Сайдкар `<имя>.access.json` рядом с документом
   (`{"access": [...]}`) читается при загрузке — документ рождается с меткой и не бывает открытым
   ни секунды. В `updated_at` сайдкар не входит: правка прав не стоит пересчёта векторов.
   `sync-access` (команда, ручка control-plane, хвост `index`) сверяет метки в индексе с
   сайдкарами и пишет расхождения `set_payload`'ом в документ и его чанки; переход «открыт →
   закрыт» пересобирает Карту.
7. **Контекст запроса — явный параметр.** `RequestContext` собирается в `pipe()` и передаётся
   через диспетчер в инструменты и поисковые вызовы; контракт обработчика инструмента —
   `(pipeline, cfg, args, ctx)`.

## Почему не иначе

- **Не фильтр после поиска.** Из 50 лучших по всему корпусу человеку может быть доступно 5 —
  ответ строится на случайном остатке. Только живая проверка без копии прав — то же самое плюс
  сотни обращений к хозяину на вопрос.
- **Не список запрещённого в запросе.** Новый закрытый документ, о котором вызывающий ещё не
  знает, был бы открыт. Разрешающие метки ломаются закрытыми.
- **Не список людей в метке.** Выдача доступа и смена состава подразделений меняли бы индекс.
  Метка называет документ и подразделения; кто их «проходит», знает хозяин прав.
- **Не группы в запросе.** Их сотни, и они живут у хозяина прав.
- **Не доверие полю без подписи.** Порт движка достижим не только из сайта; без секрета любой,
  кто до него достучался, назвался бы кем угодно.

## Конфиг

```yaml
retrieval:
  access:
    enabled: true                 # по умолчанию false — поле asker не читается
    key_env: MORAG_ACCESS_KEY     # имя переменной окружения с секретом вызывающего
    sidecar: .access.json         # метка рядом с файлом локального источника
    provider:                     # хозяин прав; без url — принципал только сам id, без живой проверки
      url: http://site.internal/api/access
      key_env: MORAG_ACCESS_OWNER_KEY
      ttl: 300
```

Поле `access` нельзя сделать фильтром агента или колонкой каталога — конфиг отвергается: перечень
значений выдал бы список принципалов.

## Замеры

- **Утечка — тест по всем путям** (`tests/retrieval/test_access_leak.py`): настоящий пайплайн и
  поисковик поверх Qdrant в памяти. Чужой, аноним и локальная учётка с тем же логином не видят
  маркера закрытого документа ни в одном пути; автор видит его в каждом (контроль самого теста);
  копия прав «открыт» проигрывает живой проверке «закрыт»; отказ на закрытый id совпадает с отказом
  на несуществующий. С отключённым фильтром падают 6 тестов из 10.
- **Цена условия в Qdrant** (dense-запрос, top-100, 15 042 чанка, вектор 2560, 50 запросов):
  без индекса по метке — 6.9 → 27–28 мс; **с KEYWORD-индексом** (его ставят `index` и
  `sync-access`) — 6.9 мс без доступа, 6.5 мс аноним, 6.5 мс «пять своих записей», 6.9 мс
  «300 принципалов, из них 30 в метках». То есть индекс обязателен, и с ним цена нулевая.
- Качество ответов со всеми правами против базы (`eval_native`) не мерилось: нужен живой агент
  с LLM. При пустых метках условие пропускает всё — выдача та же по построению.

## Границы и риски

- **Индекс и порт движка обязаны быть закрыты от сети.** Векторная база хранит тексты целиком,
  фильтры мимо неё не действуют. Это условие включения, не часть кода.
- **Кто имеет доступ к серверу, имеет доступ ко всему** — как и к ключам LLM. Шифрование ключом
  автора сломало бы поиск и сводки; не делаем.
- Короткий код документа (ADR-0025) для закрытого документа узнаётся как существующий: отказ
  `get_doc` одинаков, но разбор кода отличает «код испорчен» от «код верен». Коды агент берёт
  только из своей выдачи, утекает лишь факт существования кода, не содержимое.
- Хозяин прав недоступен — запрос не падает: принципалы сводятся к самому `id`, живая проверка
  отказывает всем документам (закрыто, а не открыто).
- Цепочка замков (ограничения по уровням дерева страниц: пройти все, внутри уровня — любой) —
  поля `access_1…` при подключении источника с такими правами. Формат «кто спрашивает» не
  меняется.
- **Структурные папки меток не несут**: имя каталога видно в `find_section` и Карте всем.
  Закрытое класть в каталоги с нейтральными именами (содержимого папка не раскрывает: её текст —
  только имя).
- Перечень значений фильтров и Карта знаний — только из открытого всем: значение, встречающееся
  лишь в закрытых документах, фильтром не выбрать. Карта и перечень на класс доступа — потом, если
  понадобится.
- Сайты поверх Open WebUI: пользователь, которого подставляет сам OWUI, становится `id` при
  секретном ключе pipelines — отдельным шагом.
