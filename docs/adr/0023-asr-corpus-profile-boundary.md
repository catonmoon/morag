# ADR-0023: Профиль корпуса — доменное из движка в репозиторий проекта

## Статус

**Предложено** (2026-08-28), не реализовано. Решение о выкате за владельцем: обезличивание базы
меняет поведение работающего прода, см. «Порядок выката».

Часть работы уже сделана и лежит в `main`: `ASR_CORPUS_DESC`, `ASR_MIN_SPEAKERS`/`ASR_MAX_SPEAKERS`
(коммит «описание корпуса и число голосов — из конфига»). Этот ADR доводит начатое до границы,
которую движок обязан держать целиком.

## Контекст

Конвейер транскрибации задумывался generic — и по сути такой и есть: диаризация, чанкинг, глоссарий,
покрытие речи и пословное выравнивание к жанру записи безразличны. Но **шесть мест, влияющих на
поведение, знают про «Капитанский мостик» или хотя бы про жанр «подкаст»**:

| файл | что зашито |
|---|---|
| `pipeline.py:349` | заголовок по умолчанию — `Капитанский мостик №N` |
| `stages/final_round.py:24` | правка терминов: «расшифровку фрагмента русскоязычного подкаста про технологии» |
| `stages/final_round.py:60,65` | сводка: «сводки одного выпуска подкаста», «сожми выпуск подкаста» |
| `stages/namer.py:18` | наминг: «Тебе дано НАЧАЛО подкаста» |
| `stages/namer.py:29` | few-shot в промпте: примеры ASR-гарбла с реальными фамилиями ведущих |
| `config.py:103` | дефолт `ASR_CORPUS_DESC` — тот же подкаст |

Пока инстанс был один, это не мешало. Появилась вторая область применения: **папка рабочих записей —
встречи, митапы, обучающие материалы вперемешку**, где заранее не известно, что за запись. На ней
доменные дефолты вредят: правка терминов, настроенная на подкаст про технологии, тянет канонизацию
не туда, а заголовок «Капитанский мостик №1» получает планёрка.

Требование владельца, ради которого пишется этот ADR: **в мораге — база, в репозиториях проектов —
детали и конфиги.**

## Решение

**Профиль корпуса** — набор доменных значений, который живёт в репозитории ПРОЕКТА (в git, без
секретов) и подключается к движку одной переменной.

```
<репозиторий-проекта>/<корпус>/asr-profile.env    # в git проекта, без секретов
  ASR_CORPUS_DESC="<чем является материал, родительный падеж>"
  ASR_ALWAYS_TERMS="<имена участников, продукты — через запятую>"
  ASR_NAME_HINTS="<примеры ASR-гарбла фамилий: «Иваанов»→«Иванов»>"
  ASR_TITLE_DEFAULT="<заголовок по умолчанию>"
```

```
~/.asr-stack.env                             # на машине, 0600, НЕ в git
  OR_KEY, HTTPS_PROXY, Bearer'ы бэкендов, пути, ASR_REGISTRY_PATH
  ASR_PROFILE=<путь к asr-profile.env проекта>
```

Разделение по адресату, а не по удобству: **секреты и раскладка машины — на машине, доменное — в
git проекта**, где его видно, ревьюят и переносят вместе с корпусом.

В движке дефолты становятся нейтральными: «записи разговора» вместо подкаста, «Транскрипт» вместо
названия подкаста, `ASR_NAME_HINTS` пустой. Пустой, а не «нейтральные вымышленные примеры»: чужие
фамилии в few-shot публичного движка — это подсказка модели в чью-то пользу, и лучше её не иметь
вовсе, чем иметь случайную.

### Что профилем НЕ является

- **Жанр записи.** Внутри корпуса встреча, лекция и митап мешаются, и разбирать их не нужно:
  стадии одинаковы, а наминг консервативен — не нашёл представлений, оставит `Speaker_N`
  (проверено: `stages/namer.py`, «не назван ни интро, ни реестром»). Автоопределение жанра —
  решение задачи, которой нет.
- **Реестр голосов.** Он не настройка, а состояние, и делится по корпусам через
  `ASR_REGISTRY_PATH`. Объединение реестров разных проектов — отдельная задача (скрипт), не эта.

## Последствия

**Хорошее.** Публичный движок перестаёт знать про чужой подкаст. Второй корпус заводится файлом,
а не форком стадий. Доменное лежит в git проекта — переносится вместе с ним и не теряется при
переезде на другую машину (сейчас `ASR_ALWAYS_TERMS` живёт только в плисте действующего
инстанса).

**Цена.** Появляется обязательный шаг настройки: инстанс без профиля работает, но хуже — глоссарий
переоткрывает термины на каждой записи и на устойчивом гарбле срывается (замерено на корпусе:
«Колодзев» ×14, `MotorMost` ×24). То есть **профиль перестаёт быть необязательным украшением** и
становится частью развёртывания.

**Риск, который и откладывает выкат.** На действующем инстансе профиля нет — доменное там лежит
в плисте launchd. Обезличив базу раньше, чем профиль доедет до этого инстанса, мы получим
следующую запись, расшифрованную без доменных подсказок: вернутся ровно те гарблы фамилий, ради
которых `ASR_ALWAYS_TERMS` и заводили.

## Порядок выката

1. Завести профиль в репозитории проекта — со значениями, которые сейчас зашиты в код и в плист
   действующего инстанса.
2. Научить `deploy/mac/stack.sh` читать `ASR_PROFILE` поверх `~/.asr-stack.env`; действующему
   инстансу прописать те же значения.
3. Прогнать одну запись с профилем и **сверить с прежней расшифровкой той же записи**: сходство
   текста по словам, метки спикеров, потери речи. Методика — в `deploy/mac/README.md`.
   ⚠️ Сравнивать по словам и с `autojunk=False`: `difflib` на репликах длиннее 200 элементов
   занижает сходство вдвое.
4. Только после этого обезличить дефолты в мораге (шесть мест из таблицы) и вынести few-shot
   в `ASR_NAME_HINTS`.
5. Прогнать `tests/asr_adaptor/` — там уже есть `test_corpus_desc.py`, дополнить его проверкой
   нейтральности дефолтов.

Шаги 1-3 безопасны и обратимы: они ничего не отнимают, только добавляют профиль. Необратим шаг 4,
и делать его стоит на неделе без выпуска.

## Альтернативы

**Оставить как есть.** Дёшево, но второй корпус тогда живёт с чужими промптами: планёрка приезжает
«Капитанским мостиком», а правка терминов ищет в ней технологический подкаст.

**Форк стадий под каждый корпус.** Отвергнуто: расхождение промптов — это расхождение качества,
и выстраданные барьеры (запрет вступлений, «остальные слова дословно», формат замен) пришлось бы
поддерживать в нескольких копиях.

**Автоопределение жанра записи моделью.** Отвергнуто: лишний вызов LLM ради решения, от которого
ни одна стадия не зависит — см. «Что профилем НЕ является».
