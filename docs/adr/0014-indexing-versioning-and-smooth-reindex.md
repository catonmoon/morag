# ADR-0014: Плавная переиндексация — replace-not-delete и ручной реиндекс по источникам

## Статус

Предложено (2026-05-17, переработано 2026-05-18). Не реализовано.

## Контекст

Применить изменение, затрагивающее **уже проиндексированные** документы (новый код
извлечения источника, другой чанкер, смена конфига), сегодня можно только через
`python -m cli.main index --reset` — он сносит коллекцию целиком. Пока корпус
пересобирается, ретривал сломан; при падении на середине — старт с нуля. Это
разрушительная big-bang-операция, и страх перед ней откладывает изменения индексации.

Конкретный триггер этого ADR: изменение `JiraSource` — алгоритм извлечения стал собирать
**другие** `Document`'ы из тех же Jira-задач. Содержимое задач в Jira не менялось, поэтому
`_is_up_to_date` (он смотрит `updated_at`, `embedder_fingerprint`, `count == total`
чанков) изменение не видит — а единственный способ его применить остаётся `--reset`
по всему корпусу, включая нетронутые Confluence и local.

Нужно: переиндексация — в том числе полная — должна быть **штатной плавной операцией**,
без сноса коллекции, прерываемой и возобновляемой.

## Рассмотренные и отклонённые альтернативы

**1. Пятистадийный DAG fingerprint'ов.** Отдельный fingerprint на каждую стадию пайплайна
(chunk / context / doc / embed) + перестройка пайплайна в resumable-вид, где стадии
скипаются индивидуально. Отклонено: точность per-stage почти не срабатывает — реальные
изменения это смена алгоритма, валящая весь DAG; цена рефактора не окупается.

**2. Авто-детекция: fingerprint'ы конфига + версии-константы кода.** Два fingerprint'а в
payload (`source_fp` от extraction-полей конфига источника, `pipeline_fp` от indexing-конфига
+ embedder'а) + ручные константы `SourceClass.PROCESSING_VERSION` / глобальный
`PIPELINE_VERSION`, бампаемые при изменении кода. `_is_up_to_date` сравнивает fingerprint'ы
и переиндексирует точечно. Отклонено сознательно: **слишком много мест, где можно ошибиться
или забыть** — классификация каждого поля конфига на selection/processing, ручной бамп
версий-констант с режимом отказа «silent staleness», семантику изменения кода система
всё равно знать не может. Цена дисциплины выше выгоды авто-детекции.

**Вывод:** триггер переиндексации — **явное действие оператора**, не автоматика. Система не
угадывает, что устарело; решает оператор, сделавший изменение. Взамен переиндексация
делается плавной.

## Решение

Три части: ручной реиндекс по источникам в Console, replace-not-delete, разделение осей
`version` / `run_number`.

### 1. Ручной реиндекс по источникам

Console, секция Sources: на каждый источник кнопка «Пересчитать» + общая «Пересчитать
всё». Оператор сам решает по характеру изменения: поменял jira-алгоритм → «Пересчитать
jira»; поменял чанкер (общий код) → «Пересчитать всё». Эндпоинт control-plane — по образцу
существующего `POST /control/rebuild-km` (scoped-операция, своя кнопка в UI).

Механика: реиндекс источника = форсить обработку всех его документов, минуя
`_is_up_to_date`. `--reset` (полный снос коллекции) остаётся как nuclear-опция, но уходит
из рутины.

### 2. replace-not-delete

Сейчас reindex документа: `delete` старых чанков → `upsert` новых — между ними окно, где
документ представлен неполно. Меняем порядок. Реиндекс документа X в прогоне R:

1. Прогнать doc-процессоры → новый `Document`.
2. Посчитать все новые чанки X, проштамповать `run_number = R`.
3. `upsert` новых чанков (R) — сосуществуют со старыми.
4. `delete` старых чанков X: `doc_id == X AND run_number < R`.
5. `upsert` точки документа X (`run_number = R`) — **последним шагом, это точка коммита**.

Точка документа упсертится последней: её `run_number` = «документ X полностью переведён в
прогон R». Пока он не обновлён, документ для резюма считается недоделанным (см. ниже).
Корпус **всегда запрашиваем** — нет окна, где документ пустой. Краткий промежуток между
шагами 3–4, где у одного документа сосуществуют старые и новые чанки (возможна лёгкая
дубль-выдача, reranker её схлопывает), допустим.

### 3. Две оси: `version` и `run_number`

Сегодня единое поле `version` (ADR-0012) бампается и при изменении контента, и при
реиндексе — две разные сущности склеены. Разводим:

- **`version` — ось контента.** Бампается ТОЛЬКО когда изменился сам документ
  (`updated_at` отличается от сохранённого). При плавном реиндексе того же контента —
  НЕ меняется. Это ось будущего архива версий (отдельный ADR; `version_status='historical'`).
- **`run_number` — ось реиндекс-прогона.** Глобальный монотонный счётчик (ADR-0012),
  штампуется на каждый upsert. Служит swap-маркером (шаг 4) и маркером резюма.

Изменение семантики `version` — это **правка логики `_prepare_document`**, не миграция:
сейчас `_stamp_payload(version=prev+1)` безусловно; делаем `prev+1` только если
`updated_at` изменился, иначе `prev`. Старые значения `version` на существующих установках
слегка «раздуты» (считали и реиндексы) — безвредно: для архива важен только порядок,
а он монотонный.

Новых полей не вводится — `version` и `run_number` уже есть в payload.

### 4. Эффорт и резюм

«Эффорт» переиндексации = довести все документы в scope (источник или весь корпус) до
`run_number ≥ N`, где N — `run_number` на старте эффорта. Эффорт может занять несколько
физических прогонов (краш, throttle, ночные прогоны).

Две **разные** роли `run_number` — не путать:

- **Селекция (резюм):** какие документы ещё не обработаны эффортом — те, у кого точка
  документа имеет `run_number < N`. Резюм обрабатывает только их; документы с
  `run_number ≥ N` пропускает (уже сделаны).
- **Swap-delete:** для обрабатываемого сейчас документа удалить старые чанки —
  `run_number < R`, где R — текущий прогон (а не N).

Control-plane персистит «эффорт для scope S стартовал на прогоне N, в процессе» в
status-файл (`FileStatusReporter` это уже умеет). После краха резюм-прогон читает N.

### 5. Устойчивость к краху и монотонность

Краш между шагами 3–5 оставляет у документа X старые и частично новые чанки. Восстановление
самоочищается:

- Точка документа упсертится последней (шаг 5) → при крахе до неё `run_number` точки X
  всё ещё `< N` → резюм X выберет → переобработает.
- Swap-delete `run_number < R` следующего прогона сметает **любой** мусор: и осиротевшие
  старые чанки, и недоделанные чанки упавшей попытки — все они с меньшим `run_number`.

**Монотонность `run_number` намеренна — это не bookkeeping, а гарантия отсутствия
коллизий.** Возобновлять прогон под тем же номером нельзя: частичные чанки упавшей попытки
и чанки новой попытки получили бы одинаковый `run_number` и стали неразличимы — swap-delete
не смог бы их развести. Растущий счётчик гарантирует, что новые чанки помечены числом,
заведомо большим всего, что лежало раньше. Поэтому реиндекс документа идемпотентен и
самоочищается, а отдельное per-document поле-генерация не нужно: оно потребовало бы той же
монотонности, но её пришлось бы добывать сканом существующих чанков — `run_number` даёт
её даром, потому что глобальный.

### Что НЕ делаем

- **Авто-детекция устаревания** — сознательно (см. отклонённые альтернативы). Цена: если
  оператор забыл переиндексировать после изменения — индекс устаревает молча. Принимается:
  реиндекс запускает тот, кто сделал изменение, сразу после него — «забыл» здесь заметнее,
  чем забытый бамп константы.
- **`_is_up_to_date` не меняется** — остаётся `updated_at` + `count == total` +
  `embedder_fingerprint` для штатного cron-sync. Реиндекс-эффорт перебивает его force-флагом.
- **`embedder_fingerprint` оставляем** — единственный авто-чек, не требующий дисциплины
  (хэш от model/dim/base_url — данные, не код, классифицировать нечего). Забыть смену
  embedder'а катастрофично, а чек уже в коде и работает.
- **Knowledge Map и BM25** — вне scope. KM перестраивается отдельной операцией
  (`rebuild-km`), BM25 строится post-indexing каждый прогон.

## Последствия

**Плюсы:**
- `--reset` уходит из рутины — переиндексация плавная, корпус не простаивает.
- Реиндекс прерываем и возобновляем: краш → резюм доделывает только незавершённое, готовое
  не переделывает.
- Реиндекс конкретного источника не трогает остальные.
- Ноль новых полей, ноль переименований, ноль миграций схемы — реюз `version` и
  `run_number`. Семантика `version` уточняется правкой кода.
- Минимум «мест, где можно забыть»: нет версий-констант, нет классификации полей конфига.

**Минусы и риски:**
- Silent staleness, если оператор забыл переиндексировать. Принимается сознательно.
- Краткое окно сосуществования старых и новых чанков одного документа при swap.
- Чанки, проиндексированные до появления `RunContext` (или голым CLI без env), могут не
  иметь `run_number` — Qdrant-фильтр `run_number < R` пропущенное поле не матчит, такие
  чанки swap не сметёт. Лечится первым же «Пересчитать всё» (проштампует всех) либо
  тривиальным backfill'ом.

## План реализации

1. **replace-not-delete.** Переупорядочить `_prepare_document` / `_chunk_document`:
   upsert новых чанков (с текущим `run_number`) → delete старых `run_number < R` → upsert
   точки документа **последним** шагом как точку коммита. Аналогично `delete_attached`.
2. **Семантика `version`.** Правка `_prepare_document`: `version = prev + 1` только при
   изменении `updated_at`, иначе `prev`.
3. **Control-plane.** Эндпоинт реиндекса по scope (источник / весь корпус) с force-флагом;
   персист «эффорт для scope S стартовал на прогоне N» в status-файл.
4. **Резюм.** При старте control-plane проверяет незавершённый эффорт; селекция документов
   для обработки — `run_number < N` по scope.
5. **Console UI.** Кнопки «Пересчитать» на каждый источник + «Пересчитать всё» в секции
   Sources; индикатор сходимости (сколько документов scope уже на `run_number ≥ N`).
6. **Backfill.** Первый эффорт проштампует чанки без `run_number`; при желании — отдельный
   тривиальный backfill.
7. **Тесты.** Swap не оставляет окна пустого документа; краш между шагами → следующий
   прогон сметает мусор; резюм обрабатывает только `run_number < N` и не переделывает
   готовое.
8. **Документация.** Обновить CLAUDE.md (секция Idempotency; убрать «⚠️ Версионирование
   индексации»; убрать «Replace вместо delete» и «Config-change detection» из TODO).
   Снять память `feedback_indexing_version_bump.md` (правило про бамп версий-констант —
   констант больше нет).
